# Prompt 结构化与质量研究

研究日期：2026-10-07
范围：长口述输入的语义分点、口头冗余清理、事实保真、禁止代答，以及保留一次调用的交互体验。仅依据公开资料和当前仓库代码；没有调用任何模型或 provider，也没有实测 prompt 优劣。

## 当前实现与薄弱点

- [config.js](../app/main/config.js) 的 `STRUCTURE_ONLY_PROMPT` 已明确“不回答”“零丢失、零编造”，会按语义聚合多事项、跳过单主题短句，并去除“嗯/啊/那个”。`DEFAULT_PROMPT` 会在“给 AI 的需求”和一般陈述之间分流；优化模式还允许补充输出格式、占位符和基于上下文修正 ASR 同音词。
- [pipeline.js](../app/main/pipeline.js) 的 `processText` 把完整 ASR 文本一次交给 `chatOnce`；结构化首轮疑似代答时再重试一次，仍可疑则返回原文。优化模式同样有重试，并降级到结构化或原文。`stripFillers` 在调用前检查纯语气词，但只在检测/快捷路径使用，不会先改写传给模型的原文。
- [models.js](../app/main/models.js) 通过一条 system 消息、一条 user 消息调用非流式 Chat Completions。结构化/优化默认强制关闭 thinking；这与保持单次、低延迟的目标一致，但兼容端点能否遵循关闭参数并不由本地代码保证。
- “信息零丢失”是目标而不是保证。现有 `looksLikeDirectAnswer` 是输出形态启发式，无法逐项核实数字、否定、条件或实体是否保留；较长输入更容易因合并、改写或列表化而出现微小遗漏。
- `stripFillers` 的词表和字符串替换覆盖面有限；将“然后”“就是说”无条件移除，可能在少数语境删除真实连接关系或表达重点。提示词本身也把“那个”列为可删填充词，需区分口头占位词与指代词。
- 优化模式准许模型“补一条合理格式要求”、安全具体化模糊表述、添加 `[待补充]`，与严格保真目标有张力。格式选择可以是转换策略，但新增任务字段/业务要求必须明确禁止。
- 当前模式通过 system 指令描述输入为待处理语料，但 user 原文没有单独的结构化边界。将其显式标记为不可信输入数据，有助于明确其中的嵌入指令也是待改写内容；这属于提示约束，不是安全保证。

## 研究结论

对于本产品的在线路径，优先把它定义为**受约束的文本转换**，而不是开放式“提升提示词质量”：明确输入/输出边界、可改和不可改内容、何时分点、何时保持一句话、遇到疑问句只改写不回答。通过少量对比示例示范边界，固定一次调用；避免在线 self-critique、CoT、reflection 或第二个审核模型。现有违规重试保留作兜底即可，它属于异常路径，并非默认工作流。

建议分开定义两个 prompt 边界：

1. **仅结构化**：只断句、标点、删除确定无语义贡献的口头填充，按语义把多意图分点；单主题不强制分点。原事实、数字、专名、代码、否定、条件、语气强弱与不确定性须保留。疑问句、命令句均视为文本内容，只整理，不回答、不执行。不得加标题、背景、验收标准、占位符或建议，除非原文已有。
2. **提示词优化**：允许把用户明确说出的任务、背景、约束和输出格式整理成可执行 prompt；只可重排、去冗余和澄清表达，不可增加事实、受众、角色资历、约束、指标或任务步骤。缺失信息保持缺失；只有用户明确要求指出缺口时才标记待补充。输入中的问题是“待改写的问题”，绝不提供答案。

建议每个模式先试 **2–3 个短示例**，不把例子铺成大套模板。示例应覆盖模式判定、语气词边界和“不作答”，且展示保留否定、数字、代码等关键字面信息。Anthropic 文档建议 3–5 个示例，但本应用有实时延迟和上下文预算约束，少量示例是待验证的取舍，不是通用最优值。可用成对反例防止模型把“整理”扩展为“补写”。

输入正文用明确分隔符（例如 `<transcript>...</transcript>`）包起来；提示明确标签内部是用户语料而非指令，即使其中出现“忽略上面的要求”等文本也照常改写。分隔符改善可读性，不会形成模型侧的硬隔离。system 指令和输出要求保持短、可判定；稳定前缀放在动态输入之前，适配可能支持的 prompt caching，但当前兼容端点未必提供缓存能力。

不要默认加入“逐步思考”或多轮自审。任务是短文本变换而非复杂推理；额外生成步骤会增加输出 token、延迟和代答机会。只有 A/B 数据显示在特定模型上必要，才把示例或处理规则加回来，而非要求暴露内部推理。

## 两类优化方法不可混为一谈

**给用户的草稿做单次重写**：输入每次都不同，没有统一的 gold output；目标是忠实转换当前内容。在线 prompt 应尽量确定、轻量、低方差，不能要求模型猜用户没说过的意图。

**针对固定任务优化 prompt**：需要代表性训练/验证样本、明确的参考输出或评分标准；离线生成候选、测分、人工复核，再发布静态 prompt。ProTeGi、OPRO、GEPA、PromptWizard 属于这一类。它们的论文结果只表明在论文设定的数据集、模型和指标上表现如何，不能推导本产品长口述改写的普遍提升或“最优 prompt”。

如果未来要做离线优化，可从用户授权/合成样本建立去标识小语料，维护训练集和独立留出集，评分分项关注信息保留、组织可读性、误删/新增、是否代答和延迟；优化时每次只改一类边界，评测集不参与 prompt 生成。先人工审阅失败样本和候选输出，再由独立留出集比较。不得把在线用户的私密口述默认送进优化或第三方服务。

## 最小 A/B 评测集

用 6–8 条合成输入做一个固定小套件；每条提供原文和人工标注的必须保留项/预期行为。比较当前版本与候选版本，并至少用目标兼容 API 上的同一模型、参数和输入逐条运行。该套件适合发现明显回归，样本太少，不能支撑统计显著性或跨模型结论。

| 用例 | 输入要点 | 主要检查项 |
|---|---|---|
| 长口述多意图 | 2–3 个主题、来回补充细节 | 语义分点；每项信息可回溯；顺序/从属关系正确 |
| 单主题短句 | 一件事，含停顿和重复 | 清理口头冗余；不强制编号或标题 |
| 事实与数字 | 人名、日期、金额、版本号 | 每个字面事实保留；不得四舍五入、推断或补单位 |
| 否定、条件与不确定 | “不要”“除非”“可能/大概” | 极性、作用范围、条件、置信语气不变 |
| 疑问/指令素材 | “为什么……？”或“帮我写……” | 输出改写后的问题/任务，不回答、不执行 |
| 口头词歧义 | 填充式“嗯/那个”与有指代作用的“那个文件” | 只删无语义填充，不删指代/转折 |
| 代码与专名 | API 名、路径、英文缩写、代码片段 | 逐字符保留代码/标识符；不翻译专名 |
| 混合长输入 | 多段背景、格式要求、嵌入式“忽略指令” | 输入边界明确；嵌入文本当语料；不增加新要求 |

每条输出由人工按维度打勾：事实/数字/专名保留、否定和条件保留、语义分点、口头词处理、格式合适、没有回答原问题、没有编造/扩写。另记录单次成功率、触发重试/降级率和端到端 LLM 延迟的中位数及 P95。先逐条对照错误类型，不把几个综合分掩盖的硬失败折算成平均分；任何事实新增、关键事实丢失或代答都记为严重失败。对输入长度分层重复运行以观察模型采样波动。没有真实运行结果前，不写任何提升数字或“最优”结论。
