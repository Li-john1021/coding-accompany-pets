# 识图实现选型：复用 MarkItDown 的视觉转文字服务模式

日期：2026-10-27。项目：Voice2Prompt。

## 1. 决定

采用 **Microsoft MarkItDown 的视觉转文字服务模式**：将图片及提取指令发送给用户配置的多模态模型，将其返回的文字作为后续纯文本模型可消费的输入。

复用对象是它内部的图片适配、请求构造、提取提示词和文字返回流程。Voice2Prompt 继续用 JavaScript 和现有模型请求基础实现，不增加 Python 文档转换服务进程。需要时再把同一个视觉转写函数封装成 MCP 工具。

本次已定位并阅读具体实现；未实现截图/识图业务代码，未做供应商效果或耗时实测。MarkItDown 项目的维护背景、核心实现简洁程度和兼容方式是选型依据，不宣称其视觉 OCR 插件已经被证明为用户最多或速度最快。插件元数据仍标为 Beta；选择的是其与核心图片转换器共有的成熟接口模式，不是整套插件依赖。

## 2. 它如何让纯文本模型间接读图

```text
图片
  → 工具内部的视觉转写服务
      → 多模态模型读图，生成文字/结构描述
  → 工具返回文本
  → 纯文本模型读取该文本，执行分析任务
```

识图服务中确实有另一个具备视觉能力的模型。纯文本模型不需要获得图片输入能力，它只接收工具转写后的文字。返回的信息质量、遗漏和错误会影响后续分析；文字模型无法自行恢复转写时遗漏的像素细节。

MCP 负责暴露工具及传递结果；图像语义转换发生在视觉后端。也存在以传统 OCR 为后端的 MCP；本项目选定的是多模态模型后端。

## 4. 确定复用的技术点

1. **直接传图片字节**：剪贴板图片转 PNG 字节，再生成 `data:image/png;base64,...`。不需要公开图床或文件 URL。
2. **图文混合消息**：同一次请求的 `content` 中放提取指令和 `image_url`，让真正支持图片输入的模型处理。
3. **提取与分析分开**：视觉层负责忠实转录及必要的图像信息描述；后续分析模型只消费返回文本。
4. **任务专用提示词**：保持原语言、文字顺序、数字、代码缩进和表格关系；看不清处标记，不擅自补字。对图表/无文字图补充客观描述，符合已确认需求。
5. **统一文字结果**：底层返回正文与错误信息，业务成功后才写剪贴板。无正文、请求失败或不支持图片时显式失败。
6. **模型可替换**：复用现有 Base URL、Key 和模型 ID；使用当前勾选了多模态的文字模型。模型能力仍以服务实际支持为准。

上述源文件没有证明某种缩图策略、缓存或并行调度能令单张截图识图更快，因此本方案不将这些包装成已验证的复用收益。

## 5. Voice2Prompt 的接入合同

建议新增独立的 `transcribeImage` 入口，概念接口为：

```text
输入：图片 PNG 字节 + 当前多模态 provider + 转写指令
内部：Data URI → 图文消息 → 一次视觉模型调用 → 正文校验
输出：成功时返回转写文本；失败时返回明确错误
```

`app/main/models.js` 可复用现有 URL 拼接、鉴权与请求基础；不经 `pipeline.processText()` 的文本重写流程。应只取最终正文，不把 reasoning 字段当转写结果。图片解码、剪贴板与模型请求放在主进程，渲染层通过现有 preload/IPC 请求操作并接收状态。

当前用户已确认的实际产品流程是：

```text
Alt+A / 截图按钮 → 框选 → 图片写入剪贴板
用户点击识图 → 多模态转写一次 → 文字写入剪贴板
```

结果已经可以交给任何纯文本模型分析。本次选型没有新增自动分析调用，也没有改变“当前所选模型勾选多模态且剪贴板有图片时启用识图”的规则；这样不会额外增加一次分析请求或让最终剪贴板内容从转写原文变成分析答案。

## 6. 效率判断与验收重点

对单张截图，第一版只做一次视觉调用；先不串接本地 OCR，也不重复请求文字模型。这样减少中间处理和请求次数，但实际速度、费用、识别效果主要由图片尺寸、所选视觉模型与服务端决定。

需在实现阶段用同一批真实截图测量：中文小字/数字准确率、代码和表格结构保留、图表信息覆盖、是否补写，以及端到端延迟。第一轮实测通过前，不把“最成熟、最多人用、最高效”当作已经建立的横向比较结论。
